Chapter 1: REST API Overview
Introduction
REST APIs  used in the application are built on the Representational State Transfer Application Programming 
Interface design. REST APIs provide an easy-to-use Web API abstraction layer for executing transactions 
supported by the Application Server. This abstraction provides simplified and selective object 
representation and method invocation. OpenAPI and OData schemas and metadata provide readable 
definitions and navigation of the API. The API is  generated from the object model and is customizable. 
These API sets provide a modern alternative to the existing WCF services, enabling you to perform 
transactions through REST API rather than using WCF. The API sets are designed to be easier to develop 
and manage programmatic and automated interactions with Opcenter EX MDD or Opcenter EX CR. They 
expose endpoints for executing Application Server transactions that are defined and exposed in the 
metadata, both default and custom, or third-party. Files needed for REST are provided as part of the 
Opcenter EX MDD or Opcenter EX CR installation.

Benefits and Operational Overview of REST API
REST APIs provide a Web API abstraction layer for executing transactions supported by the Application 
Server. REST APIs enable you to execute transactions more efficiently than if using WCF services. When 
using REST APIs, HTTP/HTTPS requests to the Application Server are performed asynchronously. 
Benefits of Using REST API
Using REST APIs provides these benefits:
• Uses standard conventions for exposing endpoints, representing data, etc.
• Keeps backend complexity hidden by abstracting services.
• Uses a simple, compact payload resulting in faster transmission and serialization times.
• Provides readable definitions and navigation of the API by using OpenAPI and OData schemas and 
metadata.
• Uses HTTP methods (GET, PUT, POST, DELETE.) to access and use data as part of the REST 
architecture, making the intent standardized and easy to understand.
• Uses the HTTP protocol for API security, making managing and integrating authentication and 
authorization simple. Secure communication through TLS/SSL is inherited from HTTP.
API Service Operational Overview
Each API service follows the same basic configuration and operational design. The services are hosted in 
separate Web applications mapped under the Default Web site.
Specifically, these are the paths:
• /modeling/api/
• /shopfloor/api/
• /query/api/
• /labels/api/
They are configured to run in their own IIS application pools.
Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the 
Opcenter Execution Core System Administration Guide for information on stopping and starting the 
services.
Upon start-up, the services retrieve the configured metadata for the CDO services and entities that they 
will expose. The services also   generate REST and/or OData metadata. Additionally, they generate the 
associated endpoint handlers for the exposed services. This is similar to the process used to produce the 
WCF services. However, the REST API services use only the subset of runtime metadata needed for the set 
of services they will handle. They also execute this  in a way that allows for  no-downtime database update 
(DBUpdate) scenarios.

Like the WCF services, the REST API services provide a pass-through mechanism to execute transactions in 
the Application Server. They use JSON-formatted payload. The definitions of request and response payload 
entities and service URLs are provided in OpenAPI- and OData metadata-formatted documents.
In the Swagger UI, the JSON documentation link for each endpoint is located right below the endpoint 
title. This provides a detailed definition of the endpoint including request and response structures. The 
JSON documentation is particularly useful if the Swagger schema fails to load due to a large model 
schema.
To  access the Swagger.json file directly, use the following URL:
https://{{server}}/{{projectName}}/swagger/EndpointName/swagger.json
Authentication is passed through to the Application Server as it is with the WCF Services. However, for the 
REST APIs, authentication is done in the authorization header using a simple base64-encoded JSON 
structure of the  user's credentials.  Refer to "Authentication" for more information.

Cross-Origin Resource Sharing (CORS) Overview
CORS is a mechanism defined by the Fetch API Specification that allows REST API to specify which origins 
are permitted to access its resources. This is essential for web security because browsers block requests 
from different origins by default for security reasons.
Only requests from origins you specify (for example, https://example.com) are allowed to access the API. If 
you try to access the API from a different origin, the request is denied due to the CORS policy. If an 
application from an unapproved origin attempts to access the API, it receives a CORS error response. This 
prevents unauthorized domains from using your API.
You can specify origins on the CORS tab in the Management Studio Configuration pane. When you click 
Save, the application updates the appsettings.json file for each REST API service (Modeling, Shopfloor, 
Query, and Labels). The application writes the information to the AllowedOrigins section:
"AllowedOrigins": [
"https://example.com"
]

Authentication
When making a request to one of the APIs, you must include an Authorization HTTP header that contains a 
Bearer token.  Authentication is based on user credentials. User credentials consist of a user name and a 
password or session ID. The user credentials are submitted using the Authorization HTTP header as a 
Bearer token with the credentials structure encoded as a base64 string. The token contains the credentials 
needed to authenticate to the Application Server. 
Note: Refer to "Authenticating with SSO SAML using Azure AD in Conjunction with REST API" if you 
access the Portal using the single sign-on (SSO) method of user authentication with the Secur-
ity Assertion Markup Language (SAML) and you want to execute transactions using REST API.
Username, Password, TimeZone, and Encryption
This is an example of the JSON structure for the user credentials if specifying user name and password:
{
"username": "UserName",
"Password": {
"value": "UserPassword",
"isEncrypted": false
},
"TimeZone":"-0500EST"
}
Replace UserName with your user name and UserPassword with your  password.
You can replace the TimeZone  value with your local TimeZone in Server Code format. Setting TimeZone  is 
optional. Refer to the list of valid TimeZone values in the TimeZones section of the \Program Files 
(x86)\Camstar\Camstar Portal\User\Settings.xml file. The application server uses the GMT TimeZone if you 
provide TimeZone in an incorrect format.
Note: Previous releases of the application used utcoffset to specify local time. The utcoffset para-
meter is still supported, but TimeZone is the preferred parameter. If you specify both utcoffset 
and TimeZone, the value specified with TimeZone takes precedence. If neither parameter is spe-
cified, the value from the server hosting the Modeling API is used.
IsEncrypted is optional, and the default setting is false. Set isEncrypted to true if you are using an 
encrypted password. Refer to "Installation and Configuration Steps" for information.

Using the AdvancedPerformEvent Endpoint
The AdvancedPerformEvent endpoint is a custom REST API endpoint available within the Modeling and 
Shopfloor namespaces. It offers powerful capabilities for orchestrating sequential custom events and 
managing staged data inputs within a single API call.
While this endpoint can be used for a wide range of scenarios, it is particularly suited for use cases 
involving multiple inputs, a sequence of events, or staged data input in which the output of one operation 
feeds into the next.
Although the endpoint's name suggests event performance, none of the JSON properties within the 
request body are strictly required. This means the endpoint offers significant flexibility:
• It can be used to simply trigger an Execute call without performing any specific events (that is, 
without firstEvent or secondEvent objects).
• If you omit the Execute path segment  from the URL, the endpoint can be used to retrieve data 
from a CDO based on the provided beforeEventData or afterEventData—without triggering any 
events or operations.

Working with List Arrays
When working with lists (arrays) in the Modeling API, it is essential to adhere to specific rules to ensure 
proper updating and maintenance of list items. The following guidelines detail how to manage and modify 
list items:
1. Order and Indexing
Lists are ordered and indexed, meaning each list item must be specified in the request body 
exactly as it exists in the database. The order of list items is crucial and must be preserved during 
updates.
For example, if you want to update a list that contains 50 rows, you can add all 50 list items to 
the body of the PUT request.
Note: An error message such as "Not all array elements have been passed in \"TheList\"" is 
returned if you do not add all list items, or if you add them in the incorrect order.
2. Property Specification
For each list item, all specified fields must be included. If a property is specified for one list item, it 
must be included for all list items to avoid unintended removal or resetting.
If a field such as Name is configured to have a unique value, you cannot have two list items in the 
array with the same Name. You cannot simply change the Name field of one list item and assign 
this value to the Name field of another list item within a single PUT request. You must first send a 
PUT request to change the value of the Name field for the first list item. Then, in a separate 
request, you can assign this value to the Name field of another list item.

Example: DataVersion
The dataVersion parameter helps prevent conflicts when multiple users modify the same object. When 
included in a PUT request, the API checks whether the provided dataVersion matches the latest version of 
the object:
PUT request to https://<servername>/modeling/api/BOMs/01110000000012a?dataVersion=1

"The object ChangeHistory with instance id '00000000000012a' has been modified by someone else.  
Please redo your changes.”
To get the current dataVersion, send the GET a specific object request so that the latest dataVersion is 
returned in the response headers.

If dataVersion is not included in the PUT request, the REST API processes the update without version 
validation.

Decimal Formats
Decimal values  per REST API standards use a decimal point as the decimal separator (for example, 99.99). 
You need to pass numbers in REST API  using only the decimal point as the decimal separator. The comma 
is  used as a decimal separator in some regions, but if you try to pass numbers using the 99,99 format, 
REST API will fail because REST API uses the comma as a delimiter.
For example, if you are using a comma as the decimal separator in the Portal, REST API shows decimal 
values correctly, but only if you pass the decimal values  per REST API standards (that is, 99.99, not  99,99). 
Therefore, if you pass 99.99 using REST API into the Portal and the Portal is configured to use a comma as 
the decimal separator, the number displays as expected (99,99).
