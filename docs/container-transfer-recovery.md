# T07 本地执行中断恢复

适用于同一本机磁盘上的计划数据库和升级后的四类转移执行入口。所有连接该数据库的旧版执行进程须先停止；不能混用旧版执行代码。不要删除、替换或单独清理数据库旁的 `.attempt-locks` 目录或锁文件，也不要在执行期间移动数据库。网络共享、多主机和数据库副本间不提供此互斥保证。

## 状态与边界

四类执行在重新校验前取得单计划非阻塞进程锁，SQLite原子领取计划时同时写入 `transfer_attempts`。锁保持到本地结果持久化结束；进程异常退出由操作系统释放锁。活跃执行期间恢复入口直接拒绝，不等待执行结束。

任务取消时保存 `unknown`、取消说明和已取得的响应/证据，再向上层传播取消。若进程崩溃或本地结果保存失败，计划可能仍为 `in_flight`。时间久、PID消失或当前数量/关系匹配均不作为服务端事务结果。

## 恢复步骤

1. 用 `get_container_transfer_plan` 读取计划、摘要、环境和原请求，保存故障日志。确认所用数据库路径正确，已停止旧版执行进程，未删除过锁文件。
2. 对 `in_flight` 调用 `recover_container_transfer_attempt(plan_id, plan_digest, evidence_reference, review_note)`，引用运维故障证据并说明恢复原因。在应用中核对原请求并明确确认；直接MCP调用方必须执行同等审批。
3. 工具必须取得同一计划进程锁，验证摘要、环境和新版尝试记录。活跃执行、错误环境/摘要、旧版缺少记录或非 `in_flight` 状态均拒绝。旧版遗留计划须停机后按独立运维流程处理，本工具不直接修改它们。
4. 成功时只把 `in_flight` 改为 `unknown`，原状态、结果、尝试编号和人工说明原子保存到 `transfer_recoveries`。所有涉及容器及新名称占用保留，原计划不可重发。
5. 继续核对服务端最终事务/审计证据。原客户端退出后服务端仍可能完成原请求。仅在人工确认最终结论后，另行调用 `resolve_container_transfer_outcome` 并提供相应证据；它会单独要求确认。恢复说明本身不能替代事务证据。后续业务操作需要新计划。

## 验证状态

模拟测试覆盖任务取消、请求进行中恢复拒绝、跨进程互斥、子进程异常退出后恢复、审计与状态更新原子性、最终结果保存失败、重叠计划仍被锁定以及恢复后单独人工核实。未执行现场业务事务；真实进程故障与服务端继续处理等情形见集中验收清单。
