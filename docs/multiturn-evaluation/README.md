# 多轮工具调用评测报告

2026-10-25。结论：常用查询、参数提取和基本审批链能运行，但多轮交互还不够稳定。此次发现并修复了一个与模型无关的旧审批处理问题，同时发现限值参数类型不清晰和重复确认等问题。不能把本次样本分数当成生产正确率。

## 用例与方法

- [38段问法清单](cases.md)：32段主用例、6段留出变体，共87条用户轮次；[结构化用例](cases.json)。这些是人工设计的合成业务问法，不是生产用户流量统计。
- 模型为配置中的deepseek-flash，真实调用流式模型接口，使用生产LangGraph、分组路由、检查点及审批恢复流程。
- MES工具输出与确认计划展示为固定夹具；生产业务函数的端到端SQLite/服务端行为不属于这层模型评测。运行时经验注入关闭，避免样本依赖本机已审核经验。
- 工具名和参数依据实际MCP schema检查；部分配置参数又经生产point_changes函数离线回放复核。
- 业务工具没有真实MES回退分支；底层HTTP仅允许配置中的模型chat/completions端点。各批没有非模型HTTP请求，没有MES对象创建或业务写入。会话和检查点放在独立work目录，不写入运行服务会话/经验库。
- 每段独立会话，段内保留真实模型回复、工具返回和审批状态。检查正确工具、具体对象和值、步骤前置条件，以及不得写入/不得重试等约束；不要求所有只读查询顺序完全一致。
- 每轮150秒、模型输出最多8192 tokens、无请求自动重试。源码摘要和实际所见工具名保存在各批results.json中。

## 主要发现与已修复项

### 1. 旧审批会忽略用户新指令：已修复

确定性回放复现：先生成温度25并进入系统审批 → 用户改为30要求重看计划 → 用户确认。旧引擎丢弃第二条指令，第三轮仍可执行25。

这不是模型参数推断问题：即使模型完全正确，审批暂停分支仍会丢消息。证据：[修复前回放](pending-before.json)、[预期失败的回归](pending-before-junit.xml)。

现在非确认的新消息会先撤销旧待审批调用、保存取消结果，再以新请求处理；确认只恢复当前绑定调用。修改数值、切换话题和口语取消都不能让后续确认认领旧调用。已增加强制进入审批的引擎回归，并验证新计划为30、只执行一次：[修复后回放](pending-after.json)。这是撤销待审批调用，并非删除业务计划或已发生事务。

### 2. 文字确认与系统确认叠加：部分改善，仍未解决

模型有时先在普通回复中询问确认，收到确认才提出执行工具，系统又拦截询问一次。已增加明确审批交互规则，让模型提出待审批调用，由系统统一展示确认。

普通提交和常用确认短语有所改善，但D08/H03在改参数后仍偶发重复确认。重点复测D08两次都需要额外一轮确认；没有在预定第三轮执行，安全门保留。不能宣称这项已稳定解决。

### 3. 限值参数数字/字符串错误：已补schema并实测

早期模型把upper_limit写为数字90/95。真实工具将限值视为表达式，要求字符串或null；早期夹具仅验证changes为dict，错误地把这些调用判通过。

用生产字段校验复核后，4个早期调用均被拒绝：[参数契约审计](configuration-contract-audit.json)。现MCP schema明确描述点/组的嵌套字段类型，常量限值也要求字符串，例如"95"；运行时验证继续保留。

最后D25重复两次，共4次真实模型调用，upper_limit全部正确写成字符串"90"/"95"并通过契约检查：[重点实测](final-focused/results.json)。这比仅修改提示词更直接，但仍需后续样本检验。

### 4. 省略领域词、改成/改为与工具暴露：已补路由

“帮我核实这次提交”没有重复“采集”，原路由可能只给只读工具；“温度改成30”也可能漏掉写工具组。已结合上下文处理明确核实和参数变更，历史查询仍只给只读工具。

首轮修复D08曾正确生成30的新计划，却提出了本轮未暴露的collect_container_data调用。这个函数确实存在且审批拦截有效，但仍属于本轮schema契约偏差，原始失败保留，后续补了“改成/改为”路由。

### 5. 只问状态时主动提出核实：仍未解决

H05第二次实测中，用户只问计划当前怎样，模型主动加载写工具并提出verify_collection_submission审批。该工具会改变本地计划终态，因此不该把它混同只读状态查询。

系统暂停了该调用，没有执行核实；下一条非确认问题会撤销旧审批。最终重点复测仍复现一次，需要继续区分“查询状态”和“申请核实”，不能把有审批就等同于意图正确。

## 评测标准的人工复核

[人工复核记录](manual-review.json)保留自动误判，不覆盖原始分数：

- D23回复“要判定合格，还缺以下条件”，实际明确不能作质量结论，被粗略关键词规则误判为宣称合格；已缩窄规则并加测试。
- D25早期被宽松夹具判通过，生产参数回放才发现错误；现在加入实际字段契约检查。
- D24早期只说“小数”，新版schema列明decimal/float后，模型追问具体类型是合理行为，不能为了得到工具调用而鼓励猜测。当前问法已明确decimal后另测，历史原文不改。

因此自动评分只用于筛查；工具/对象/值/审批可做确定性断言，解释性中文结论仍应人工抽查。当前小样本不能给出可靠的生产误调用率。
